# PlannerCopilot 演进记录 —— 从极简对话循环到上线产品

> 本文档记录 PlannerCopilot 从 2025 年 11 月起步至今的完整演进过程。
> 组织方式是**真实迭代顺序（六轮）**：每一轮都始于一个具体痛点，终于一个可验证的解法。
> 文中所有设计决策均可对照仓库源码复核；每轮末尾附相关源码文件索引。
>
> 另附：**技术储备专题**——主线之外按专题深入研究过的进阶方向（评估、安全、重试等），
> 经评估后未全部进入线上版本，取舍理由见各专题说明。

| 轮次 | 主题       | 解决的痛点                                   |
| ---- | ---------- | -------------------------------------------- |

## 第 1 轮：对话骨架 —— 手搓 Function Calling 双循环

### 痛点与选择

起步时 LangChain/LangGraph 已经成熟，直接调框架是最快的路。但项目的首要目标是
**掌握 Agent 底层机制**——不理解底层，框架报错时只能干等。因此选择基于
OpenAI 兼容 SDK 手写工具调用循环。

动手之前先做了一件事：拆开 SDK 看封装结构。`client` 只是持有认证信息和 httpx
连接池，`chat.completions` 是资源路由代理，真正干活的 `create()` 是拼 URL、
组请求体、发 POST、反序列化返回。想通这层，"SDK 没有魔法"才落地——后来踩的
"返回的是 pydantic 对象、不能用下标访问"的坑，根源也在这里。

### 形态

双层循环：

- **外层**：多轮对话循环。history 列表开头放 system prompt（人格与行为边界），
  每轮追加用户输入与助手回复；
- **内层**：工具调用循环。模型返回 `tool_calls` → 按注册表分发执行 → 结果以
  `role: "tool"` + `tool_call_id` 回填 → 再问模型，直到模型给出最终文字回答。

两个关键保护从第一版就在：

- **轮次上限**（`MAX_TOOL_CALL_ROUNDS = 6`）：模型可能陷入反复调用工具的死循环，
  没有上限就是持续烧 Token。达到上限优雅退出并提示用户拆分问题——熔断思想；
- **异常不炸穿**：工具参数是非法 JSON、模型幻觉出不存在的工具名、工具执行抛异常，
  全部捕获后以 `{"error": ...}` 形式喂回模型，让它自我纠正，对话不中断。

### 演进细节（第一版 → 当前版）

- 结束判断：`not msg.tool_calls` → `finish_reason != "tool_calls"` 双重判断，更稳健；
- 注册表查找：直接索引（幻觉工具名会 KeyError 崩掉）→ `.get()` + 错误回喂；
- 消息回填：SDK 返回的 pydantic 对象用 `model_dump(exclude_none=True)` 落成纯 dict——
  排除 None 字段，避免回传 API 时字段为 null 被服务端拒绝；
- `tool_call_id` 强配对：一轮可能有多个并行工具调用，靠 id 对应结果与调用。

📎 源码：`agent_core.py`（`_run_tool_loop` / `_execute_tool`）

## 第 2 轮：记忆系统 —— 先解决"装不下"，再解决"记不住"

### 短期记忆：滑动窗口 → 摘要压缩

对话历史就是一个 list，聊多了必然撑爆上下文窗口。第一版解法是滑动窗口
（只保留最近 N 轮），但硬截断会丢信息——规划师聊学生情况，前面说过的位次、
选科被截掉，后面的建议就错了。

升级为**摘要压缩**：对话超过阈值后，调一次大模型把老对话总结成一段话，
用摘要替换原始记录。信息有损，但关键结论保住。当前参数：超 20 轮触发，
保留最近 6 轮原文。

### 长期记忆：跨对话的学生跟进

规划师隔天还要回来继续跟同一个学生——需要跨对话记忆。早期版本用本地 JSON
文件存历史，启动时读出并调大模型提取关键事实（选科、位次、目标路径）注入
messages。这套机制在第 4 轮上 PostgreSQL 后做了简化（见该轮说明），但
"历史 → 提炼 → 注入上下文"的主链路从那时保留至今。

📎 源码：`memory.py`（`_summarize` / `append_turn` / `format_memories_for_context`）

## 第 3 轮：业务落地 —— 规则工具 + 关键词检索 + RAG

前两个轮次都是通用能力，这一轮把升学规划业务融进来，分三个层次：

### 3.1 报考资格规则判断（三个工具）

强基计划 / 综合评价（南开·天大）/ 港澳升学三条路径的资格初判：输入选科组合、
预估位次、竞赛奖项，输出结构化结果（满足条件 / 缺失条件 / 建议动作 / 数据说明）。
这三个工具**零外部依赖**——不依赖数据库、不依赖知识库，是整个系统里唯一
"不会因为外部服务挂了而出错"的模块。

### 3.2 院校卡片关键词检索

本地 JSON 知识库（`data/tianjin_programs.json`），覆盖"有没有、是什么"类问题，
是"先粗后精"里的粗层。

### 3.3 RAG 简章问答（本轮核心，内部又进化了三次）

"南开强基校测占综合成绩多少比例"这类问题，答案藏在简章具体条款里，光靠模型必编。
第一版 RAG 很朴素：文本按空行分块，Embedding 后存进内存 numpy 矩阵，每轮对话
强制检索、结果拼进 user 消息。跑通后三个毛病逐一暴露、逐一改掉：

1. **存储：内存索引 → pgvector**。内存矩阵进程重启即丢，每次启动要对知识库
   全量 Embedding，又慢又烧钱；pgvector 持久化，且与学生档案共用一个
   PostgreSQL，少运维一套组件；
2. **分块：空行切 → 三级分块引擎**。段落优先 → 超限时按句子边界切 → 单句仍超限
   才字符硬切兜底；块间保留 50 字重叠窗口防跨块断句；页码、纯数字行等噪声碎片
   直接过滤。旧版"硬切不看标点，会把一句话从中间切断"的问题就此解决；
3. **接入方式：每轮必检 → 注册成工具按需调用**。每轮强制检索的代价是闲聊也白跑
   Embedding、无关片段污染上下文。改成 `answer_from_brochure` 工具后由模型
   自己判断要不要查原文——这一步是从 naive RAG 到 agentic RAG 的分水岭。

**两个实测踩坑记录**：

- **ivfflat 近似索引在小数据量下静默漏召回**：3 条数据配 lists=100 的索引，
  检索时漏掉本该排第一的结果——不报错，只返回错的。因此当前不建近似索引，
  数据量小（几百到几千块）时 PostgreSQL 顺序扫描精确且够快；等涨到数万条再按
  官方建议建索引（lists ≈ 行数/1000，查询前 `SET ivfflat.probes`）；
- **检索纪律故障**：模型曾不调用检索工具、凭内置知识直接断言某校专业"只认正式
  志愿"。为此在系统提示词中加入检索优先原则：凡涉及具体院校数据必须先调工具
  核实；查不到时按"定性说明 → 通用参考（标注未核验）→ 核查路径"三段式回答，
  不允许无来源的具体断言。

**同期的一个选型决策**：Embedding 走 SiliconFlow API（bge-large-zh-v1.5）而非
本地部署——文本块量级小，API 按量计费成本接近零、免运维；且 DeepSeek 无
embeddings 接口，对话与向量化本就需要两条独立配置轨道（见 `config.py` 双轨道设计）。

📎 源码：`tools.py`、`knowledge_base.py`、`rag_system.py`、`prompts.py`、`config.py`

## 第 4 轮：数据层重构 —— PostgreSQL + Pydantic

### 持久化与记忆分层

历史对话不能只存在一个内存列表里。引入 PostgreSQL 后，记忆重新分成三层：

- **短期记忆**：Redis，按 session 过期（TTL），超 20 轮触发摘要压缩。
  所有 Redis 操作做了防御性异常处理——Redis 挂了退化为"本轮不带记忆"
  照常回答，绝不崩溃；
- **长期记忆**：咨询要点表，按学生 + 标题去重覆盖（一个学生只保留最新一轮要点，
  不会越攒越多）；
- **完整留痕**：咨询记录表，全量保存每轮问答。

早期 JSON 时代的"LLM 提取结构化事实注入"在这一轮做了简化：改为要点覆盖存储，
注入机制保留、提取环节去掉——演进过程中砍需求也是常态，够用优先。

### Pydantic 统一数据词汇表

散装 dict 在多文件间传递时，键名写错一个字符就是隐蔽 bug。这轮引入 Pydantic
统一全部数据模型：学生档案（`StudentProfile`）、资格判断结果（`EligibilityResult`）、
对话轮次（`ConversationTurn`）等，全项目只有一份"词汇表"。

LLM 交互边界统一收口到单一序列化函数（`_serialize_tool_result`）：内部代码读
类型化字段，喂给大模型时经 `to_display_dict()` 转成中文键 dict 再序列化。
以后新增工具只要遵守这个约定，序列化层零改动。

📎 源码：`database.py`、`models.py`、`memory.py`、`agent_core.py`（序列化收口）

## 第 5 轮：工程化 —— 从"自己能用"到"别人也能用"

- **建档状态机**：学生建档是确定性流程，用状态机（`enrollment_bot.py`）逐步引导
  收集信息，而不是大模型自由对话——可控、可单测、省 Token。咨询阶段同样做成
  状态流转：初次建档 → 规划进行中 → 报名申请中 → 已完成，只进不退；
  Agent 检测到规划师开始研究简章细节（首次触发 `answer_from_brochure`）时
  自动推进阶段；
- **三个入口，一套核心**：`main.py` 命令行（开发调试）、`app.py` Streamlit 工作台
  （规划师日常用）、`api.py` FastAPI（对外服务）。关注点分离：全项目只有
  `agent_core.py` 一个文件认识 OpenAI SDK，加新工具只改 TOOLS 列表和注册表
  各一行——注册表模式，符合开闭原则；
- **多租户**：FastAPI 用 `Depends` 注入做 API Key 鉴权（鉴权逻辑改动只动一个
  函数）；所有查询带 `planner_id` 过滤实现数据隔离；查别人的学生统一返回 404
  而不是 403——403 会暴露"这个 ID 存在"；
- **可观测性**：接入 Langfuse，span / generation / tool 三级链路追踪 + Token
  用量与成本统计。做了一层薄封装（`observability.py`）：SDK 从 v2 到 v4 接口
  大变时只改封装层一个文件；未配置 Key 时空装饰器静默降级，不刷认证警告。
  LLM 调用单独抽函数标 `as_type="generation"`——只有这个类型 Langfuse 才换算
  Token 成本；
- **完整 CRUD**：补齐更新/删除接口。删除学生按"先子后父"级联（子表外键未配
  CASCADE）；更新走字段白名单（主键、归属、建档时间不可改）。

📎 源码：`enrollment_bot.py`、`api.py`、`observability.py`、`database.py`

## 第 6 轮：部署上线 —— 从项目到产品

- **Dockerfile 层缓存优化**：先只复制 `pyproject.toml`、装依赖，再复制源码——
  改一行代码不再触发几分钟的依赖重装，只有复制源码那层重新构建；
- **docker-compose 四服务编排**：app（Streamlit）+ backend（FastAPI）共用同一
  镜像（单镜像多容器），postgres（pgvector 官方镜像）+ redis 带健康检查；
- **网络收敛**：数据库与 Redis 不映射公网端口（只在容器网络内互通），应用端口
  只绑 127.0.0.1，全部流量必须过宿主机 Nginx——HTTPS、域名、访问日志统一在
  那一层管；
- **细节决策**：CMD 用 exec 形式（streamlit 直接成为 1 号进程，能收到 stop 信号
  优雅退出）；`PYTHONUNBUFFERED=1`（日志实时输出，`docker logs` 排障不被缓冲区
  误导）；全部服务 `restart: unless-stopped`（崩溃自动拉起）。

📎 源码：`Dockerfile`、`deploy/docker-compose.prod.yml`、`deploy/nginx-streamlit.conf`

## 附：技术储备专题（主线之外的深入研究）

与业务主线并行，还按专题研究过一组进阶方向，经评估后**未全部进入线上版本**。
取舍原则：工程化不是堆料，是按需选择。

| 专题       | 研究内容                                                     | 线上取舍                                                     |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 评估与观测 | 离线评估脚本（回归集 + LLM 裁判）、调用链日志                | 观测落地为 Langfuse；离线评估因测试集规模不足未上线          |
| 安全与风控 | 提示词注入检测、PII 脱敏、RAG 边界标记、工具权限分级、Token 预算熔断、输出审查 | 业务为受信规划师小范围使用，保留了轮次上限、降级、访问密码等基础防护，完整防线作为储备 |
| 工程化深化 | 流式调用、主备模型降级、会话持久化与多用户隔离               | 多用户隔离已落地（planner_id 体系）；流式输出在 Streamlit 场景收益有限，暂缓 |
| 结果可验证 | 工具统一返回协议 + 机器校验后再回填                          | RAG 场景以"来源标注 + 检索纪律"软约束为主，机器校验作为下一步方向 |
| 异常重试   | 指数退避重试；**幂等守卫：只包 LLM 调用、永不包工具执行**（LLM 调用问两次无副作用，工具执行可能有真实副作用——转账重试就是转两次） | 当前以"错误回喂模型自我纠正"为主，自动重试作为储备           |
